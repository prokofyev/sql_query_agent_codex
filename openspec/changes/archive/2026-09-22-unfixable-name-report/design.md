## Context

См. `proposal.md` — «Why». Здесь только то, что определяет подход.

Текущее устройство ветки проверки имён:

```
extract_and_check -> needs_fix --unknown не пуст--> prepare_fix -> confirm_fix -> measure
                                \-- иначе ------------------------> measure
```

`needs_fix` (src/sql_query_agent/agent/nodes.py) смотрит только на `result["unknown"]`, а
`check_entities` (src/sql_query_agent/tools/schema_check.py) создаёт `UnknownName` независимо от того,
нашлись кандидаты или нет. Поэтому «имя не найдено» и «имя исправимо» сейчас одно и то же условие.

Что уже готово и на что можно опереться:

- `UnknownName.candidates` — пустой список и есть признак «замен нет»; менять модель данных не нужно.
- `check_entities` уже возвращает `unknown_tables` и для колонок указывает `table`, поэтому текст
  сообщения собирается из имеющихся данных.
- `RunStatus` (src/sql_query_agent/run/report.py) — `StrEnum` со свойством `is_terminal`; ветка
  отказа от исправления (`status="fix_declined"`) показывает, как добавляется терминальный исход.
- `RunView` (src/sql_query_agent/ui/view.py) — чистые функции, поэтому показ сообщения и скрытие
  карточки исправления проверяются без браузера.
- `_status` в report.py выводит `FAILED` для всего, что не попало в известные случаи, и подставляет
  `error` из предупреждений. Новый исход нужно назвать явно, иначе он станет «сбоем».

Ограничения, важные для решения:

- Узел с `interrupt()` при возобновлении перезапускается целиком, поэтому проверка «есть ли чем
  исправлять» должна решаться в маршрутизаторе, а не внутри узла подтверждения.
- Требование спеки «сессия завершается» означает отсутствие точки остановки: пользователю нечего
  подтверждать, значит `interrupt()` не вызывается и прогон сразу терминален.
- Метки метрик не должны получать значений высокой кардинальности; имена таблиц и колонок в метки не
  попадают, только итоговый статус.

## Goals / Non-Goals

**Goals:**
- Один маршрутизатор решает, исправимо ли ненайденное имя, опираясь на наличие кандидатов.
- Сообщение о ненайденных именах собирается детерминированно и попадает в отчёт, API и UI одним путём.
- Новый исход — обычный завершённый прогон: терминальный статус, запись в журнал, счётчик метрик.

**Non-Goals:**
- Отдельный вызов модели ради формулировки сообщения: текст и так известен из результата проверки.
- Новая точка `interrupt()` или новый шаг подтверждения.
- Изменение порога схожести и алгоритма подбора кандидатов.
- Правка запроса «частично», когда часть имён исправима, а часть нет: смешанный случай сразу
  завершает сессию.

## Decisions

### Исправимость решается функцией над `unknown`, а не полем в состоянии

Вводится чистый предикат вида «есть ли ненайденные имена без кандидатов» и второй — «исправимы ли
все ненайденные имена». Маршрутизатор после проверки имён пользуется ими, а не заглядывает в
`unknown` напрямую. Текст сообщения собирается отдельной чистой функцией по тому же списку
`UnknownName`: таблица → «таблица X», колонка → «колонка Y таблицы Z».

Почему так: детерминированная функция тестируется юнит-тестом без графа, без модели и без базы, а
маршрутизатор остаётся тонким. Альтернатива — считать исправимость в `prepare_fix` и оттуда уходить в
терминальное состояние: это раздувает узел, который обязан остаться «вычислительным», и требует
проверки условия внутри ветки, где уже случился вызов модели.

### Терминальный исход — отдельный статус прогона

Добавляется статус вида «имена не найдены, замен нет» (рабочее имя `unknown_unfixable`), терминальный
по `is_terminal`. `_status` в report.py получает явную ветку для него, поэтому исход не превращается
в `FAILED`, а `error` остаётся пустым: сообщение — это результат проверки, а не сбой.

Почему не переиспользовать `FIX_DECLINED`: пользователь ничего не отклонял, и в журнале «отклонено»
было бы неверным истолкованием.

### Сообщение живёт в отчёте, а не собирается заново в UI

Готовый текст кладётся в `RunReport` (и в `RunReportSchema`), UI только отображает его в отдельном
блоке. Клиент UI собирает `RunReport` из ответа API (`src/sql_query_agent/ui/client.py`), поэтому
сообщение должно пройти через контракт, иначе внутрипроцессный UI и API разойдутся.

Почему не собирать текст во `view.py` из `unknown`: тогда внешние клиенты API и NiceGUI получали бы
разные формулировки одного и того же исхода.

### Показ без карточки исправления

`RunView.fixed_sql` остаётся `None`, потому что модель не вызывалась, поэтому карточка исправления и
кнопки решения скрыты уже существующим условием `visible = bool(view.fixed_sql)`. Достаточно добавить
в `RunView` текст сообщения и выводить его, когда он непустой; поле ввода разблокируется общим
правилом (прогон терминален).

## Risks / Trade-offs

- [Пользователь с опечаткой в таблице и без кандидатов больше не получит даже попытки исправления] →
  Так и задумано: подставлять имя наугад опаснее, чем попросить исправить запрос вручную; в сообщении
  есть точное имя, которое надо поправить.
- [Смешанный случай завершает сессию, хотя одно имя исправимо] → Осознанный выбор в пользу простоты и
  отсутствия полу-исправленного запроса; расширение до частичной правки потребует отдельного изменения
  спеки.
- [Текст сообщения — новый кусок пользовательского вывода, который может разойтись с именами в
  запросе] → Имена берутся из результата проверки, то есть ровно из запроса; в тестах проверяется,
  что в сообщении нет выдуманных имён.
- [Новый статус в метках Prometheus повышает кардинальность] → Одно новое значение на существующей
  метке `status`; текст запроса и имена по-прежнему в метки не попадают.

## Migration Plan

Изменение обратно совместимо по данным: схема базы, формат существующих записей журнала и набор
метрик не меняются. Новое значение статуса появляется в отчётах и записях журнала, поэтому
потребители, разбирающие `status` по закрытому списку, должны быть готовы к ещё одному значению.
Откат — возврат ветки исправления к прежнему маршруту; записи журнала остаются читаемыми, так как
добавление статуса не меняет структуру записи.
