## Context

См. `proposal.md` — Why, и change `fix-identifier-attribution`, который вводит исправление
неоднозначных колонок квалификатором. Текущий ответ модели — `SqlFix` с одним полем `sql`, а замены
восстанавливает `run/report.py::find_replacements` эвристикой по тексту: имя считается заменённым,
если оно исчезло из нового текста, а один из предложенных кандидатов появился целым токеном.
Вспомогательные `contains_identifier` и `IDENTIFIER_CHARS` реализуют проверку «отдельным токеном».

Замеры на реальных прогонах (GigaChat-2-Max):

- структурированный ответ `{sql, replacements}` через `with_structured_output` даёт верные замены
  3/3 на опечатке в колонке и 3/3 на опечатке и в таблице, и в колонке — заявленное совпало с
  фактическим различием текстов;
- на неоднозначной колонке модель заявила `brand_id → product.brand_id`, и это верно, а текущая
  эвристика замену не находит (старое имя осталось в тексте);
- на случае «менять нечего» модель 3/3 нарушила запрет придумывать имена и заявила
  `brand_name → brand.brand_name`, хотя кандидатом был только `brand_id`; ущерб ограничен тем, что
  модель честно описала то, что сделала, но текст запроса при этом исказила.

Отсюда два вывода: доверять только заявлениям модели нельзя и полагаться только на текст тоже
нельзя. Нужны оба источника и сверка.

## Goals / Non-Goals

**Goals:**
- Получать от модели явный список замен вместе с текстом запроса.
- Показывать пользователю только те замены, которые подтверждаются фактическим различием текстов.
- Корректно распознавать квалификацию колонки как замену, не путая её с отсутствием изменения.

**Non-Goals:**
- Изменение промпта извлечения имён и разрешения принадлежности колонок (это change
  `fix-identifier-attribution`).
- Изменение формата карточки исправления в интерфейсе и модели отчёта: поля замен не меняются.
- Полноценный SQL-парсер: различие считается по токенам текста, а не по разобранному дереву запроса.

## Decisions

### D1. Ответ модели — `{sql, replacements}`

Единственный вызов исправления возвращает и текст, и список замен с полями «старое имя», «новое имя»
и «что это» (таблица или колонка). Список замен перестаёт угадываться постфактум.

Вложенная модель списка замен обязана иметь docstring: без описания `with_structured_output` в
GigaChat падает с `ValueError: Incorrect function or tool description. Description is required.`
Проверено на прототипе.

Альтернативы: заявлять замены отдельным полем и не сверять (отклонено — модель придумывает имена в
случае «менять нечего»); оставить один текст (отклонено — эвристика не видит квалификацию).

### D2. Замена подтверждается различием текстов

`difflib.SequenceMatcher` по списку токенов даёт точную последовательность правок: для квалификации
это вставка токена (`([], ['brand'])` в нужном месте), для опечатки — замена токена
(`(['product_colr_id'], ['product_color_id'])`). Замена показывается пользователю, если модель её
заявила и различие текстов её подтверждает.

Почему токены, а не строки: квалификация `brand_id → product.brand_id` при посимвольном сравнении
выглядит как вставка подстроки, из-за которой текущая проверка «отдельным токеном» и не срабатывает.
Разбиение на токены идентификаторов и знаков препинания убирает эту сложность.

Кандидаты из результата проверки остаются белым списком для модели, но для подтверждения замены
используется текст, а не список: так замена с квалификатором, которого не было среди кандидатов,
корректно попадает в отчёт.

### D3. Удаление эвристики

`find_replacements`, `contains_identifier` и `IDENTIFIER_CHARS` удаляются: после D1 и D2 они не нужны
и именно они дают неверный результат в обоих направлениях. Их тесты переписываются на проверку
подтверждения замен по тексту.

## Risks / Trade-offs

- **Модель заявит замену, которой нет** → подтверждение по различию текстов отбрасывает такое
  заявление; пользователю показывается только то, что есть в исправленном запросе.
- **Модель изменит текст, но не заявит замену** → изменение попадёт в показанный запрос, но в списке
  замен его не будет. Риск ограничен: пользователь видит исправленный запрос целиком и может
  отказаться.
- **Разбиение на токены ошибочно склеит соседние идентификаторы** → различие строится по
  последовательности токенов, поэтому склейка двух правок в одну отразится в списке замен как одна
  замена; на наблюдаемых случаях (опечатка, квалификация, замена таблицы) различие остаётся корректным.
- **Структурный ответ удорожает вызов** → один дополнительный список в том же вызове, отдельного
  обращения к модели не добавляется.

## Migration Plan

Изменение внутреннее, формат отчёта и интерфейса не меняется. Порядок работ: сначала изменение
`fix-identifier-attribution` (иначе квалификация неоднозначной колонки не появится в тексте), затем
это. Откат — возврат одиночного поля `sql` и прежней эвристики.
