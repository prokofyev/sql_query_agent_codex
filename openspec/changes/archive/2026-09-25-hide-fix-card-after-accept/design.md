## Context

См. `proposal.md` — Why. Сейчас `RunView.fixed_sql` заполняется из отчёта, пока в состоянии графа
есть `fixed_sql`, а карточка исправления в `ui/app.py` показывается по `bool(view.fixed_sql)`. Это
остаётся верным и на шаге предложения индекса, и в итоговом отчёте, поэтому принятое предложение
висит на экране до конца прогона.

Статус при этом берётся из `STATUS_TEXT` по статусу отчёта, а `run_decision`, в отличие от
`run_submit`, не показывает промежуточный экран: до ответа сервера на экране остаётся статус
«Нужно решение пользователя».

## Goals / Non-Goals

**Goals:**
- После принятия исправления не показывать ни запрос-предложение, ни список замен — ни во время
  обработки, ни на шаге индекса, ни в итоговом отчёте.
- Показывать «Обработка запроса», пока система обрабатывает решение пользователя.

**Non-Goals:**
- Изменение отчёта, API и журнала: исправление и его замены остаются в данных прогона.
- Изменение поведения при отказе от исправления и при решениях по индексу.

## Decisions

### D1. Скрытие — признак экрана, а не очистка данных

`RunView` получает признак «исправление принято» из решений отчёта
(`report.decisions["fix"] == "accepted"`), а карточка показывается по новому свойству
`shows_fix_proposal`: `fixed_sql` задан и исправление не принято.

Почему не очищать `fixed_sql`: он нужен переносу принятого запроса в поле ввода
(`decision_input_text`), а API и журнал по-прежнему обязаны содержать исправление как запись о том,
что система сделала. Скрытие — свойство показа, а не данных.

Альтернатива — прятать карточку только на время обработки решения (первый разобранный вариант,
отклонён пользователем: предложение возвращалось бы на шаге индекса).

### D2. Решение пользователя показывается как обработка

`run_decision` получает текст запроса и перед обращением к серверу показывает `pending_view`, как это
делает `run_submit`. Модель ожидания при этом пустая (`fixed_sql` не задан), поэтому карточка
исправления на время обработки тоже не видна.

Почему в `run_decision`, а не в разметке: порядок показа уже задан в этих функциях, и он общий для
отправки запроса и передачи решения.

## Risks / Trade-offs

- Пользователь, принявший исправление, больше не видит список замен — замена видна только в тексте
  запроса в поле ввода. Это принятая плата за чистый экран; данные замен остаются в API и журнале.
- При отказе карточка остаётся видимой: так пользователь видит, что именно предлагалось.

## Migration Plan

Миграций нет: изменение только в показе экрана.
