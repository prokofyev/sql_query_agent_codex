## Context

См. `proposal.md` — Why. Текущий аргумент инструмента `check_schema` — список «таблица — колонки»
(`domain.ColumnNames`): модель обязана решить, какой таблице принадлежит колонка, и инструмент
доверяет этому решению. Замеры на реальных прогонах (GigaChat-2-Max) показали, что модель делает это
неверно и стабильно: `brand_name` в запросе
`select brand_name, product_name from product join brand on brand.brand_id = product.brand_id`
она 4/4 раза отнесла к `product`. Правки промпта («проверяй во всех таблицах запроса») не помогли —
атрибуция осталась неверной 4/4. Промпт с буквальным примером про `brand_name` дал 3/3 верных
ответа, но это подгонка под конкретный случай.

Второе наблюдение: колонки `brand_id`, `product_id`, `product_size_id`, `product_color_id` есть сразу
в нескольких таблицах демо-базы. Запрос `select brand_id, product_name from product join brand on
brand.brand_id = product.brand_id` падает в PostgreSQL с `column reference "brand_id" is ambiguous`,
а инструмент этого не замечает: `unknown` пуст, прогон доходит до замера и завершается
`status: failed`.

## Goals / Non-Goals

**Goals:**
- Убрать атрибуцию из задачи модели: принадлежность колонки таблице определяет инструмент по схеме.
- Ловить неоднозначные колонки до замера и исправлять их квалификатором.
- Искать похожие имена колонок по всем таблицам запроса, а не по одной предполагаемой.

**Non-Goals:**
- Изменение графа, шага подтверждения исправления и интерфейса: неоднозначность проходит через
  существующий `schema_fix`.
- Полноценный разбор SQL парсером: состав таблиц и колонок по-прежнему определяет модель.
- Изменение порога схожести и лимита подсказок.
- Изменение того, как определяются выполненные замены (это отдельный change `structured-fix-report`).

## Decisions

### D1. Извлечение без атрибуции: таблицы, алиасы, колонки как записаны

Аргумент инструмента становится структурой из трёх плоских списков:

- `tables` — настоящие имена таблиц запроса, без алиасов;
- `aliases` — пары вида `"b=brand"` (алиас=настоящая таблица), поле необязательное: модель иногда
  возвращает его пустым;
- `columns` — колонки ровно так, как они записаны, вместе с квалификатором, если он был.

Рассмотренные альтернативы:

- `{name, tables: [...кандидаты...]}` — модель пропускала `tables` (5 прогонов из 7 вернули пустое
  поле). Отклонено.
- Только правка промпта при текущей структуре — 4/4 неверная атрибуция. Отклонено.
- Разбор SQL парсером — противоречит действующему требованию не использовать штатные средства СУБД
  для разбора и выходит за рамки изменения.

Проверка новой структуры: 3/3 стабильных извлечения на шести формах запроса, включая
квалифицированные колонки и записи вида `brand.brand_id` без алиаса. Текущее требование спеки
«передавать список таблиц и относящихся к ним колонок» заменяется на «таблицы, алиасы и колонки».

### D2. Разрешение принадлежности — детерминированное, в инструменте

Порядок разрешения для каждой колонки:

1. Колонка с квалификатором → владелец задан квалификатором напрямую; алиас разворачивается в
   настоящее имя таблицы по `aliases`.
2. Колонка без квалификатора, есть ровно в одной таблице запроса → владелец — эта таблица.
3. Колонка без квалификатора, есть более чем в одной таблице запроса → неоднозначность (см. D3).
4. Колонки нет ни в одной таблице запроса → ненайденное имя, кандидаты ищутся по колонкам всех
   таблиц запроса.

Проверка прототипа: на запросе пользователя результат `ok` без ненайденных имён; все 12 пресетов
проходят без ложных срабатываний; `product_namme` → `product_name` (96), `product_colr_id` →
`product_color_id` (97). Опозначаемость отдельного слова `brand_name` без `join brand` остаётся
прежней: кандидат `brand_id` (67) — это корректное поведение для запроса без `brand`.

### D3. Неоднозначность — это находка, исправляемая квалификатором

Неоднозначная колонка попадает в результат проверки как отдельная запись с признаком
неоднозначности и списком таблиц, где она есть. Такая запись считается исправимой, поэтому прогон
идёт в `prepare_fix`, а не к замеру.

Почему через существующий шаг подтверждения: пользователь видит исправленный запрос целиком и
принимает решение там же, где принимал бы по опечатке. Граф, интерфейс и модель отчёта не меняются.

Формулировка промпта исправления дополнена явным требованием квалифицировать неоднозначную колонку
именем таблицы из схемы. Проверено: с этой фразой модель добавляет квалификатор 5/5, без неё — 1/3.
Выбор таблицы: 4/4 — `product.brand_id`.

Серьёзность неоднозначности: PostgreSQL считает такой запрос ошибочным, поэтому «оставить как есть и
замерить» — не вариант; наблюдаемое поведение сейчас — падение замера.

### D4. Поиск кандидатов для ненайденной колонки — по колонкам всех таблиц запроса

Пул вариант берётся из колонок всех таблиц запроса, а не только из таблицы, к которой колонка стояла
рядом. Это закрывает вторую половину исходной проблемы: колонка-владелец может лежать в соседней по
`join` таблице, и замена должна находиться.

Колонки отсутствующей таблицы по-прежнему ищутся среди колонок таблиц-кандидатов: если у таблицы нет
кандидатов, её колонки не проверяются и в ненайденных остаётся только таблица.

### D5. Модель по-прежнему одна: инструмент остаётся белым списком для замен

Требование «модель MUST NOT придумывать имена, которых нет среди предложенных кандидатов»
сохраняется. Для неоднозначности кандидат — квалификатор из числа таблиц, в которых колонка реально
существует, и это тоже имена из схемы, а не выдумка модели.

## Risks / Trade-offs

- **Модель ошибётся в составе таблиц или колонок** → инструмент всё равно проверит то, что получил;
  новые проверки (неоднозначность, поиск по всем таблицам) ловят часть ошибок атрибуции, но
  пропущенная таблица останется непроверенной. Существующее предупреждение о пропущенном вызове
  инструмента сохраняется.
- **Неоднозначная колонка будет исправлена на «не ту» таблицу** → запрос останется валидным по схеме
  и запустится, но может вернуть другие строки. Пользователь видит исправленный запрос и может
  отказаться; требование к модели — квалифицировать существующей таблицей, а не выдуманным именем.
- **Рост числа ложных неоднозначностей** → признак срабатывает только при совпадении имени колонки в
  нескольких таблицах запроса без квалификатора; колонки с квалификатором не затрагиваются.
- **Смена схемы аргумента инструмента** → обновляются тесты-фикстуры модели (`tests/fakes.py`) и
  интеграционные тесты проверки имён.

## Migration Plan

Изменение внутреннее: внешние интерфейсы, состояние графа и формат отчёта не меняются. Откат —
возврат прежней структуры аргумента и прежнего промпта.
