## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Здесь только то, что определяет подход.

Окружение проверено на месте:

- Локальный PostgreSQL 18.3 (Homebrew), база `products` уже засеяна: `brand` 102 строки,
  `product` 1000, `sku` 100 000, `product_size` 3, `product_color` 2. Вторичных индексов нет вообще —
  ни один внешний ключ не покрыт индексом. Роль `prokofyev` имеет право `CREATE`.
- Соседний проект `chgk_agent` задаёт конвенции стека: src-layout, `pydantic-settings` с вложенным
  `.env`, `prometheus-client`, `structlog`, ruff (line-length 100), UI ходит в API внутрипроцессно через
  `httpx.ASGITransport`, интеграционные тесты пропускаются без базы.
- Креденшелы GigaChat есть в `chgk_agent/.env`.
- Версии: `langgraph` 1.2.11, `langgraph-checkpoint-postgres` 3.1.0, `langchain-gigachat` 0.5.1,
  `nicegui` 3.17.

Пять родственных проектов в окружении (`sql_query_agent_{google,qwen,sol,z}`) решают близкую задачу.
Полезное, что из них взято: приём «индекс внутри транзакции с откатом» (`z`) и общая структура
инструмента проверки имён (`qwen`). Что осознанно не повторяется: `EXPLAIN` без `ANALYZE`, из-за
которого невозможно измерить ускорение (`sol`), и `InMemorySaver`, теряющий сессию при перезапуске.

## Goals / Non-Goals

**Goals:**
- Сквозной цикл «проверка имён → исправление → замер → индекс → замер → разница» с двумя точками
  решения пользователя.
- Честные измерения: прогрев и многократные повторы, медиана как итог, выбросы не смещают результат.
- Правдоподобный учебный набор из пяти запросов, включающий случаи «индекс не помог» по двум разным
  причинам.
- Сессия переживает перезапуск процесса за счёт checkpoint'ов в базе.

**Non-Goals:**
- Переформулировка запроса (rewrite) — отложена.
- Проверка эквивалентности результата — не нужна, пока нет rewrite.
- Разбор SQL через AST — разбор и правку делает модель.
- Изменение демо-данных: откат применяется всегда, состояние `public` не меняется.
- Аутентификация, многопользовательский режим, автомасштабирование.

## Decisions

### Инструменты вызываются моделью, а не узлами графа

Требование: модель извлекает имена и передаёт их инструменту, инструмент возвращает ненайденные имена
с кандидатами, модель правит запрос. Это обычный tool-calling, а не хардкод шагов в узлах.

Альтернатива (жёсткие узлы без `bind_tools`) отвергнута: она не соответствует требованию.

Следствия, которые надо заложить:

- У GigaChat `tool_choice="any"` не поддерживается (`chat_models/gigachat.py:931`) — доступны только
  `auto`, `none` и конкретное имя. Поэтому **нельзя гарантировать**, что модель вызовет инструмент.
  Согласно спецификации это не ошибка, а случай с предупреждением: обработка продолжается.
- GigaChat отклоняет несколько вызовов инструментов в одном сообщении
  (`chat_models/gigachat.py:271`: *GigaChat API does not support multiple tool calls in a single
  message*). Поэтому на узел — не более одного доступного инструмента, чтобы модель не выбирала не тот.
- `gigachat_fix_schema` не умеет `Union`/`anyOf` и требует `properties` у объектов, иначе провайдер
  возвращает 422. Аргументы инструментов держим простыми: `entities: list[{table: str, columns:
  list[str]}]`.

### Три инструмента, по одному на узел

- `check_schema(entities)` — читает `information_schema`, сверяет имена, для ненайденных подбирает
  кандидатов через `rapidfuzz`, возвращает только данные (без вызовов модели внутри).
- `measure_query(sql)` — безопасный замер: read-only транзакция, прогрев, N повторов, медиана.
- `apply_index(sql, index_ddl)` — `BEGIN` → `CREATE INDEX` → замер → сравнение → `ROLLBACK`.

Инструмент проверки имён намеренно **не** вызывает модель: модель вызывает его. Раннее прочтение задачи
было обратным, и оно отвергнуто пользователем.

### HITL через `interrupt()` и `AsyncPostgresSaver`

Две точки решения: после исправления запроса и после предложения об индексе. Состояние — в
`AsyncPostgresSaver`, схема `agent`.

Тонкость, которую надо учесть в реализации: LangGraph при резюме **перезапускает узел целиком**
(`langgraph/types.py:851`: *The graph resumes from the start of the node, re-executing all logic*).
Значит логика внутри узла с `interrupt()` должна быть идемпотентной или кэшированной, иначе вызовы
модели и замеры повторятся после каждого решения пользователя.

`AsyncPostgresSaver.setup()` создаёт таблицы без квалификатора схемы и использует
`CREATE INDEX CONCURRENTLY`, поэтому схема задаётся через `search_path` в строке подключения, а setup
выполняется на autocommit-соединении.

### Замер: прогрев, повторы, медиана

Проверено на живой базе, восемь прогонов одного запроса: `8.15 8.48 7.54 7.81 7.43 7.24 7.31 7.61`, и
на прогретом кэше `7.79 10.01 8.16 7.59 7.25 7.43 7.49 24.04`. Один выброс дал **3 кратную** ошибку
относительно медианы.

Вывод: одиночный замер не даёт честного «до/после». Минимум — прогрев плюс N повторов и медиана.

Безопасность замера без AST обеспечивает сама СУБД: `EXPLAIN ANALYZE` реально исполняет запрос, но
внутри `begin read only` запись отклоняется (`cannot execute INSERT in a read-only transaction`).
Дополнительно ограничиваем ввод запросами `SELECT`/`WITH` и ставим таймаут.

Отдельно: `EXPLAIN` **без** `ANALYZE` запись не отклоняет — он только планирует, поэтому как защита не
годится.

### Набор демонстрационных запросов определён измерением

Пять запросов выбраны по реальным замерам на базе `products` (три прогона, медиана, откат):

| Запрос | До, мс | После, мс | Ускорение | Что происходит |
|---|---|---|---|---|
| `where product_id = 42` | 8.39 | 0.15 | 56x | Bitmap Index Scan |
| `join + where p.brand_id = 7` | 38.56 | 0.97 | 40x | Bitmap Index Scan |
| `count(*) join + brand_id between 1..20` | 48.99 | 8.77 | 5.6x | Index Only Scan |
| `where product_color_id = 1` | 15.02 | 14.90 | 1.0x | Seq Scan: в колонке 2 значения |
| агрегат по 3 таблицам, `group by` | 182.01 | 162.95 | 1.1x | Hash Join: узкое место в агрегате |

Два последних — разные причины отсутствия ускорения, и это ядро учебной ценности: агент обязан уметь
сказать «индекс не поможет», а не выдумать индекс на каждый запрос.

### Схемы в базе `products`

- `public` — демо-данные, не изменяются.
- `agent` — таблицы checkpoint'ов LangGraph.
- `metrics` — audit-журнал прогонов.

Две разные сущности метрик: audit-строка на прогон (для разбора и демонстрации) и счётчики/гистограммы
Prometheus (для наблюдения за процессом). Текст запроса в метки Prometheus не попадает — только в
audit-журнал.

### Известная стоимость операции

`CREATE INDEX` на 100 000 строк выполняется около 15 секунд. Это заметная пауза для интерактивного
интерфейса, поэтому в UI нужен признак выполняющейся операции, а на операцию — таймаут.

## Risks / Trade-offs

- **Модель не вызвала инструмент** (следствие отсутствия `tool_choice="any"`) → по спецификации
  продолжаем с предупреждением; проверка имён не считается пройденной.
- **Повторное исполнение узла после резюме** дублирует вызовы модели и замеры → делать шаги узла
  идемпотентными, кэшировать результат замера в состоянии.
- **Шум измерений** искажает «до/после» → прогрев, несколько повторов, медиана; в отчёте показывать
  минимум и максимум, чтобы пользователь видел разброс.
- **Опечатки в именах таблиц** не имеют подсказок от СУБД (`relation "skuu" does not exist` без
  `HINT`), в отличие от колонок → подбор кандидатов делаем сами через `rapidfuzz` по
  `information_schema`, не полагаясь на текст ошибок СУБД.
- **Локаль сервера меняет текст ошибок** (`lc_messages = en_US.UTF-8`) → текст ошибок СУБД не парсим
  и не закладываем в логику.
- **Модель может предложить индекс, который не поможет** → это допустимый исход по спецификации:
  показываем честные величины и причину; метрика фиксирует случай «без ускорения» отдельно.
- **Длительное создание индекса** → таймаут и индикация в UI.
- **Ошибка записи в журнал** не должна ломать обработку → запись в журнал обёрнута так, что сбой
  логируется, но пользователю отдаётся результат.

## Migration Plan

Проект новый, миграции данных не требуются. Порядок:

1. Создать схемы `agent` и `metrics` в базе `products` (идемпотентно).
2. Убедиться, что демо-данные в `public` соответствуют ожиданиям по объёму; при отсутствии — создать.
3. Запустить setup checkpoint-хранилища на autocommit-соединении.

Откат: удаление схем `agent` и `metrics`. Схема `public` не затрагивается, поэтому откат безопасен.
