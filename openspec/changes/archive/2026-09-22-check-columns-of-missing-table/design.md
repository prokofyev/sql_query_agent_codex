## Context

См. `proposal.md` — «Why». Здесь только то, что определяет подход.

Текущая проверка сущности в `check_entities` (`src/sql_query_agent/tools/schema_check.py`):

```
for entity in entities:
    if catalog.has_table(entity.table):
        ... проверить каждую колонку ...
        continue
    unknown_tables.append(entity.table)
    unknown.append(UnknownName(TABLE, candidates=suggest(entity.table, все таблицы)))
    continue            <<< колонки этой сущности не проверены
```

Замер на подставных данных для `select * from sku2 where product_id2 = 42`:

- `unknown` = только таблица `sku2` (кандидат `sku`, 85.7), `checked_columns = 0`;
- модель правит таблицу и оставляет `product_id2`;
- замер падает, прогон получает `status = failed`.

Сопоставление замен в `find_replacements` (`src/sql_query_agent/run/report.py`) требует, чтобы новое имя
встречалось в исправленном запросе и отсутствовало в исходном. Для `sku` → `sku2` и `product_id` →
`product_id2` второе условие ложно, поэтому список замен пуст, хотя правка применена.

Ограничения, важные для решения:

- Каталог — единственный источник данных (`information_schema`), подсказки СУБД не используются.
- `can_fix_all` требует кандидата для каждого ненайденного имени: добавление колонки без кандидатов
  автоматически переводит прогон в терминальное завершение `unknown_unfixable`. Это уже существующее
  поведение, менять его не нужно.
- Терминальное завершение по неисправимым именам реализовано и проверено; здесь оно переиспользуется.
- Замена выполняется моделью, поэтому проверка имён должна передать ей все имена, которые нужно
  исправить, — иначе модель не может починить то, о чём не знает.

## Goals / Non-Goals

**Goals:**
- Ненайденная колонка попадает в результат проверки независимо от того, найдена ли её таблица.
- Пул кандидатов для такой колонки остаётся ограниченным и осмысленным, а не всей схемой.
- Список замен отражает фактически применённые правки, включая случай «новое имя — подстрока старого».

**Non-Goals:**
- Маппинг ошибок СУБД в понятные сообщения: при корректной правке замера с ошибкой имён не возникает.
- Отдельный статус «исправлено одно из двух имён».
- Поиск колонок по всем колонкам схемы: пул кандидатов ограничивается таблицами-кандидатами.
- Изменение порога схожести и алгоритма подбора (`token_set_ratio`).

## Decisions

### Колонки отсутствующей таблицы проверяются по колонкам таблиц-кандидатов

Порядок в ветке отсутствующей таблицы: сначала подобрать таблицы-кандидаты, затем собрать их колонки и
по этому пулу проверить каждую колонку сущности. Если кандидатов у таблицы нет, поведение прежнее:
единственное ненайденное имя — таблица.

Почему не «все колонки схемы»: на реальной базе `products` оба пула дают один и тот же ответ
(`product_id` 95.2), но на большой схеме пул из всех колонок приносит кандидатов из посторонних таблиц,
а подсказка теряет связь с исправляемой таблицей. Пул из кандидатов не растёт с размером схемы.

Почему кандидатов у таблицы должно быть несколько: при опечатке `sku2` единственный кандидат `sku`
достаточен, но для имени вроде `product_prices` пул из колонок `product` и `product_size` даёт более
полезные подсказки, чем колонки одной таблицы.

### Колонка сущности с недостающим именем проверяется и при ненайденной таблице

Если колонка отсутствует среди колонок таблиц-кандидатов, она добавляется в `unknown` как обычная
ненайденная колонка с указанием таблицы из запроса. Дополнительная логика не нужна: `can_fix_all`
уже решает, исправлять её или завершать сессию.

Альтернатива — при отсутствии кандидатов у таблицы не проверять её колонки: это компромисс на случай
очень больших схем, но он не нужен, пока пул ограничен таблицами-кандидатами, а пустой пул коротко
замыкает ветку.

### Сопоставление замен по границам идентификатора

Новое имя считается применённым, если встречается в исправленном запросе отдельным токеном: соседние
символы слева и справа не являются символами идентификатора (буква, цифра, знак подчёркивания).
Старое имя, наоборот, должно встречаться в исходном запросе отдельным токеном — иначе `sku` внутри
`sku2` ошибочно считался бы присутствующим.

Почему не регулярные выражения по всему тексту: SQL-текст содержит строковые литералы и кавычки, где
совпадение не является идентификатором. Проверка соседних символов решает задачу без разбора SQL и без
новых зависимостей; полноценный разбор отвергнут как несоответствующий требованию «разбор SQL штатными
средствами СУБД не используется» и как избыточный для поиска подстроки.

Почему вообще не отказаться от условия «старого имени нет в исходном запросе»: без него любая замена
считалась бы выполненной, даже если модель ничего не поменяла. Условие сохраняется, меняется только
способ сравнения.

## Risks / Trade-offs

- [Колонки ненайденной таблицы проверяются по кандидатам, и при неудачном подборе таблиц пул колонок
  окажется нерелевантным] → Имя колонки попадёт в ненайденные без кандидатов, и сессия завершится с
  сообщением — это безопаснее, чем правка половины запроса и падение на замере.
- [Расширение проверки увеличивает число ненайденных имён и чаще приводит к терминальному завершению] →
  Так и задумано: неполная правка сейчас приводит к ошибке замера, что хуже явного сообщения.
  Существующие тесты на исправимые запросы не затрагиваются, потому что у них таблица найдена.
- [Проверка по соседним символам не идеальна для имён в кавычках или с другим регистром] → Имена в
  запросе и каталоге сравниваются как есть, как и раньше; регистр не нормализуется ни в текущем коде,
  ни в этом изменении.
- [Список замен станет непустым там, где раньше был пуст] → Это и есть цель: пользователь перестанет
  видеть «правку без замен». Формат строки замены не меняется.

## Migration Plan

Поведение меняется только для запросов, где таблица не найдена. Совместимость по данным сохраняется:
схема базы, формат отчёта и записи журнала не меняются, новых полей не добавляется. Откат — возврат
ветки отсутствующей таблицы к пропуску колонок и к сравнению по подстроке.
