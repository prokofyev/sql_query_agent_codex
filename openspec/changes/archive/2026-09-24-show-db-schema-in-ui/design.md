## Context

См. `proposal.md` — «Why». Здесь только то, что определяет подход.

Текущее состояние:

- Библиотека пресетов уже переехала во внешний YAML (`resources/presets.yaml`), путь настраивается
  через `SQA_PRESETS__PATH`, загрузчик — `presets.py` с валидацией и понятными ошибками.
- Интерфейс NiceGUI: `ui/app.py` держит разметку и порядок действий, `ui/view.py` — чистые функции
  модели экрана, `ui/client.py` — внутрипроцессный клиент API. Логика проверяется без браузера.
- Страница `/ui/`: одна карточка с полем ввода и списком пресетов, ниже — карточки статуса,
  исправления, индекса и результата.
- `db/catalog.py` читает схему из `information_schema` для проверки имён — это инструмент агента,
  он к отображению схемы отношения не имеет.

Демо-схема `products` (после последней заливки): `brand` — 1 000 строк, `product` — 20 000,
`product_size` — 50, `product_color` — 2, `sku` — 100 000.

## Goals / Non-Goals

**Goals:**
- Панель схемы над полем ввода: псевдографика со столбцами, связями и числом строк.
- Схема — внешний файл рядом с пресетами; правка файла меняет панель без правки кода.
- Отсутствие или повреждение файла не ломает интерфейс.
- Один контракт: и браузер, и внешние клиенты получают схему через API.

**Non-Goals:**
- Живой запрос числа строк к базе: значения статичны и живут в файле (решение пользователя).
- Автоматическая отрисовка схемы из `information_schema` и синхронизация с реальной базой.
- Отдельная страница или вкладка: панель показывается на той же странице `/ui/`.
- Замена или дополнение проверки имён: `db/catalog.py` не меняется.

## Decisions

### Источник схемы: отдельный файл `resources/schema.yaml`

Файл рядом с пресетами, путь настраивается (`SQA_SCHEMA__PATH`, по умолчанию
`resources/schema.yaml`). Формат — словарь с полями `caption` (необязательная подпись) и `diagram`
(обязательный рисунок в псевдографике, block scalar `|`).

Псевдографика хранится как готовый текст, а не собирается из структуры «таблицы — колонки — связи»:
рисунок в файле читается глазами и правится вручную, а генератор пришлось бы писать и тестировать
ради пяти таблиц. Пользователь выбрал именно такой вариант: при перезаливке данных или смене базы
схему перерисовывают руками.

Альтернативы: (B) таблица-структура с автогенерацией рамок — код ради разового рисунка;
(C) генерировать из `information_schema` на лету — противоречит решению «статичные цифры», вдобавок
панель ломалась бы при недоступной базе.

Почему отдельный файл, а не секция в `presets.yaml`: состав пресетов и рисунок схемы меняются
независимо, а пресеты описаны списком, куда словарь схемы не вписывается без развилки парсера.

Пример содержимого:

```yaml
caption: Схема демо-базы products (число строк — снимок на момент заливки)

diagram: |
  +----------------------------------------------+
  | brand — 1 000                                |
  |----------------------------------------------|
  |   brand_id                               PK  |
  |   brand_name                                 |
  +----------------------------------------------+
                          |
                          | brand_id: 1 -> N
                          v
  +----------------------------------------------+
  | product — 20 000                             |
  |----------------------------------------------|
  |   product_id                             PK  |
  |   product_name                               |
  |   brand_id      FK -> brand.brand_id         |
  +----------------------------------------------+
                          |
                          | product_id: 1 -> N
                          v
  +----------------------------------------------+
  | sku — 100 000                                |
  |----------------------------------------------|
  |   sku_id                                 PK  |
  |   product_id          FK -> product.product_id      |
  |   product_size_id     FK -> product_size.product_size_id
  |   product_color_id    FK -> product_color.product_color_id
  |   added_at                                   |
  +----------------------------------------------+
             ^ N                       ^ N
             | 1                       | 1
  +--------------------------+  +--------------------------+
  | product_size — 50        |  | product_color — 2        |
  |--------------------------|  |--------------------------|
  |   product_size_id    PK  |  |   product_color_id   PK  |
  |   product_size_name      |  |   product_color_name     |
  +--------------------------+  +--------------------------+
```

Точную ширину рамок фиксирует реализация; важно, что рамки и стрелки выровнены в моноширинном
шрифте, а число строк стоит в заголовке каждой таблицы.

### Загрузчик: отдельный модуль, а не расширение `presets.py`

Схема — не пресет: у неё другая форма (словарь, а не список) и другие правила. Отдельный модуль
`schema_diagram.py` с моделью `DatabaseSchema(caption, diagram)` и `load_schema(path=None)`.
Отсутствующий или пустой файл даёт `None` (панель не показывается), повреждённый — `SchemaError`
с понятным текстом; это зеркалит поведение `presets.py`, но не смешивает две сущности в одном файле.

Правило «повреждённая схема не показывается» то же, что у пресетов: частичный рисунок вводит в
заблуждение сильнее, чем его отсутствие.

### Доставка: эндпоинт `GET /schema`

API отдаёт `{"caption": ..., "diagram": ...}`. Интерфейс берёт панель оттуда тем же путём, что и
пресеты, — контракт один для браузера и внешних клиентов, а внутрипроцессный клиент не дублирует
чтение файла.

- Файл отсутствует или пуст → `200` с пустыми полями (как пустая библиотека пресетов).
- Файл повреждён → `500` с кодом `schema_unavailable` (как `presets_unavailable`).
- Интерфейс на любую из этих веток реагирует одинаково: панель скрыта, поле ввода работает.

### Панель: чистая функция модели экрана + карточка в разметке

В `ui/view.py` — чистая функция, собирающая текст панели (подпись + рисунок) и признак «есть схема».
Разметка в `ui/app.py` добавляет карточку первой в `index()` и скрывает её, когда схема пуста.
Логика остаётся в чистых функциях, поэтому проверяется без браузера — как остальные ветви экрана.

## Risks / Trade-offs

- [Статичные цифры устаревают после перезаливки данных] → Осознанное решение пользователя: цифры —
  часть рисунка, при изменении базы схему перерисовывают вручную. В README и в подписи файла
  указывается, что число строк — снимок, а не живое значение.
- [Псевдографика ломается при правке: рамки перестают сходиться] → Рисунок хранится целиком и
  правится в редакторе; тест проверяет лишь непустоту и наличие заголовков, а не геометрию.
- [Схема расходится с реальной базой и вводит в заблуждение] → Панель подписана как снимок;
  источник схемы виден по настройке пути.
- [Повреждённый файл роняет страницу] → Загрузчик различает «пусто» и «повреждено», API отдаёт
  ошибку, а интерфейс прячет панель и оставляет ввод доступным.
- [Отдельная настройка и модуль плодят дублирование с пресетами] → Дублируется структура
  (загрузка, валидация, ошибка), а не сущность; общий код абстрагировать не за что.

## Migration Plan

1. Добавить `resources/schema.yaml` с рисунком и подписью.
2. Добавить настройку `SQA_SCHEMA__PATH` и загрузчик `schema_diagram.py`.
3. Добавить `GET /schema` и метод клиента интерфейса.
4. Показать панель вверху страницы, скрывая её при пустой схеме.
5. Обновить README и `.env.example`.

Откат: убрать файл или очистить настройку — панель исчезнет, остальное поведение не меняется.
