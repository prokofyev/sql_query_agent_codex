## Context

См. `proposal.md` — «Why». Здесь только то, что определяет подход.

Текущее состояние демо-базы `products` (проверено на живой базе):

| Таблица | Строк | Селективные колонки |
|---|---|---|
| `sku` | 100 000 | `product_id` — 1 000 значений |
| `product` | 1 000 | — (мелкая) |
| `brand` | 102 | — (мелкая) |
| `product_size` | 3 | — (3 значения) |
| `product_color` | 2 | — (2 значения) |

Индексы — только пять первичных ключей. Диапазонных колонок нет.

Что показали замеры на временных копиях этой схемы (`EXPLAIN (ANALYZE)`, декоррелированные колонки):

- `sku.product_id` (1 из 20 000 товаров) — ускорение с ~6 мс до ~0.02 мс.
- `product.brand_id` (1 из 1 000 брендов) — с ~6 мс до ~0.05 мс.
- `sku.product_size_id` (1 из 50 размеров, ~2 000 строк) — с ~6 мс до ~1.3 мс.
- `sku.added_at` (диапазон 7 дней из 730) — с ~40 мс до ~1.1 мс.
- `sku.product_color_id` (2 значения) — ускорения нет ни до, ни после создания индекса.

Ограничение, найденное на замерах: индекс создаётся и замеряется в одной транзакции без `VACUUM`,
поэтому visibility map пуст и планировщик не может выбрать `Index Only Scan`. Покрывающий индекс
дал бы ускорение не за счёт index-only scan, и на этой схеме отдельного сценария для него нет.

Второе ограничение: время выполнения классифицируется как «без ускорения», если диапазоны замеров
перекрываются (`ranges_overlap` в `domain_comparison.py`). Слишком быстрые запросы (доли миллисекунды)
попадают в этот случай даже при наличии ускорения.

## Goals / Non-Goals

**Goals:**
- Демо-схема, на которой индекс окупается по нескольким разным колонкам.
- Библиотека из 12 пресетов, часть которых ускоряется разными индексами.
- Пригодность агента для произвольной базы: библиотека не зашита в код.
- Автоматическая защита обещания «каждый пресет ускоряется» там, где демо-форма присутствует.

**Non-Goals:**
- Покрывающий индекс и index-only scan (см. ограничение выше).
- Наращивание `sku` ради более крупного демо: при 1 млн строк низкоселективный индекс по цвету
  начинает реально ускорять `count(*)`, и демонстрация «индекс не помогает» ломается.
- Воспроизводимый скрипт заливки: наполнение разовое, в репозиторий не кладётся.
- Изменение промптов модели, графа и алгоритма предложения индекса.
- Удаление обработки случая «индекс не помогает»: он остаётся для свободного ввода.

## Decisions

### Демо-данные: одноразовая ручная заливка

Наполнение выполняется вручную в сессии `psql` и нигде не хранится: пользователь выбрал вариант A.
SQL фиксируется здесь как справка, чтобы было видно, о какой форме данных говорят замеры и пресеты.

Целевые объёмы:

| Таблица | Было | Стало | Зачем |
|---|---|---|---|
| `brand` | 102 | 1 000 | индекс по `product.brand_id` |
| `product` | 1 000 | 20 000 | `brand_id` → 1 000 значений |
| `product_size` | 3 | 50 | индекс по `sku.product_size_id` |
| `product_color` | 2 | 2 | демонстрация «индекс не помогает» |
| `sku` | 100 000 | 100 000 | без изменений, плюс колонка `added_at` |

Заливка (справочный SQL, выполняется разово и вручную):

```sql
-- 1. Справочник размеров: 3 -> 50
insert into product_size (product_size_id, product_size_name)
select g, 'size-' || g from generate_series(4, 50) g;

-- 2. Бренды: 102 -> 1000
insert into brand (brand_id, brand_name)
select g, 'brand-' || g from generate_series(103, 1000) g;

-- 3. Товары: 1000 -> 20000, бренд распределён по товарам
insert into product (product_id, product_name, brand_id)
select g, 'product-' || g, ((g * 2654435761) % 1000) + 1
from generate_series(1001, 20000) g;

-- 4. Дата добавления SKU с разбросом на 730 дней
alter table sku add column added_at timestamptz;
update sku set added_at = now() - (interval '1 day' * (((sku_id * 2654435761) % 730)));
alter table sku alter column added_at set not null;

-- 5. Выравнивание распределений и статистика
update sku set product_id = ((sku_id * 2654435761) % 20000) + 1;
update sku set product_size_id = ((sku_id * 2654435761) % 50) + 1;
analyze;
```

Множитель `2654435761` — чтобы значения колонок не были коррелированы между собой: при выводе
`product_id` и `product_size_id` из одного `sku_id` планировщик считает колонки зависимыми, и индекс
по размеру выглядит ненужным. Ручной `analyze` обязателен: без статистики планировщик не выберет новые
индексы.

Альтернативы: (B) закоммитить `resources/demo_seed.sql` — отвергнуто пользователем, раз наполнение
разовое; (C) Python-генератор — лишний исполняемый код там, где хватает SQL.

### Библиотека пресетов в YAML

Пресеты переезжают из кортежа `PRESET_QUERIES` в файл `resources/presets.yaml`. Настройка
`SQA_PRESETS__PATH` задаёт путь, значение по умолчанию — `resources/presets.yaml`.

Формат файла: список словарей с обязательными полями `id`, `title`, `sql` и необязательным `note`.
Обязательные поля без значения — ошибка загрузки с понятным текстом.

Почему файл, а не код: состав библиотеки — свойство конкретной демонстрационной базы, а не логики
агента. Файл позволяет менять демо без правки кода и без пересборки, и это же снимает формальную
привязку агента к одной базе.

Почему YAML, а не JSON или TOML: многострочный SQL читается в YAML заметно лучше (block scalar
`|`), а `pyyaml` уже есть в дереве зависимостей транзитивно. JSON заставил бы экранировать переводы
строк, TOML — городить массивы таблиц.

Отсутствующий или пустой файл даёт пустую библиотеку, и это не ошибка: агент должен работать на любой
базе, где демо-пресетов просто нет. Некорректная запись (нет `id`, `title` или `sql`) — ошибка
загрузки: повреждённый пресет пользователю показывать нельзя.

Альтернатива: держать пресеты в базе (`metrics` или отдельная схема) — отвергнуто, лишняя связность и
миграции ради статичного списка.

### Состав библиотеки

Двенадцать пресетов, разложенных по четырём рычагам:

| Рычаг | Индекс | Пресеты |
|---|---|---|
| товар | `sku(product_id)` | счётчик SKU товара, страница SKU с сортировкой, сводка по списку товаров, соединение с названием товара, цепочка из трёх таблиц, топ-N на товар с оконной нумерацией |
| размер | `sku(product_size_id)` | фильтр по размеру, раскладка по размерам через соединение |
| дата | `sku(added_at)` | недавно добавленные SKU страницей, число добавленных за период |
| бренд | `product(brand_id)` | счётчик товаров бренда, страница товаров бренда |

Итого 6 + 2 + 2 + 2 = 12: требование «не менее десяти» выполнено с запасом, и все формы выборки
из спеки покрыты.

Пресеты по размеру, дате и бренду — новые; часть пресетов по товару заменяется, чтобы библиотека не
выглядела однообразной. Пресеты, фильтрующие по низкоселективному `product_color_id`, в библиотеку не
попадают: они противоречили бы требованию «каждый пресет ускоряется».

### Проверка обещания библиотеки после удаления тестов

Тесты, завязанные на форму текущей базы, удаляются: счётчики строк, низкоселективный `product_color_id`,
«каждый пресет ускоряется индексом по `product_id`». Обещание спеки остаётся без защиты, поэтому
взамен добавляется тест, который **пропускается**, если демо-форма в базе не обнаружена (нет колонки
`sku.added_at` или к `sku.product_size_id` меньше порогового числа значений). Так и «любая база»
поддерживается, и обещание библиотеки проверяется там, где оно применимо.

## Risks / Trade-offs

- [Пресеты привязаны к форме локальной демо-базы и на чужой базе просто не ускоряются] → Принято
  осознанно: пресеты демонстрационные, для чужой базы есть свободный ввод; это отражено в README.
- [Малые абсолютные времена делают ускорение неотличимым от шума] → `product` поднят до 20 000 строк,
  чтобы бренд-пресеты имели измеримую базу; тест проверяет ускорение и не даст добавить слишком
  быстрый пресет.
- [Демонстрация «индекс не помогает» ломается при дальнейшем росте `sku`] → `sku` остаётся 100 000
  строк; для демо «нет ускорения» используется `select *`, у которого диапазоны замеров перекрываются
  устойчивее, чем у `count(*)`.
- [Потеря индексов при повторной заливке] → Заливка разовая и ручная, повтор не предполагается;
  демо-база не воспроизводится из репозитория.
- [`added_at` заполняется `now()`] → Даты «уезжают» со временем, и диапазоны в пресетах вида
  «за 7 дней» перестанут отбирать строки, если база простояла долго без обновления. → Пресеты
  используют широкие окна (7 и 30 дней), а заливка задаёт разброс на два года.

## Migration Plan

1. Перевести пресеты в `resources/presets.yaml`, добавить настройку пути.
2. Удалить тесты, привязанные к форме базы; добавить условный тест обещания библиотеки.
3. Обновить README.
4. Выполнить разовую заливку демо-базы вручную (справочный SQL выше).
5. Проверить прогон пресетов на залитой базе.

Откат: пресеты возвращаются в код, заливка откатывается вручную (удаление добавленных строк и колонки
`added_at`). Автоматического отката нет, так как наполнение разовое.
